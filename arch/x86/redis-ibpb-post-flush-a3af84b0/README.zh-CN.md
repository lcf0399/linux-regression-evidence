# Redis ZPOPMIN：IBPB安全刷新后的持续性能代价

**发现来源：MMTests原生Redis benchmark，不是模型生成场景。**
本材料对应[补充审阅R07的Redis部分](../../../candidate/additional-review/README.zh-CN.md)，
不增加独立缺陷计数。

状态（2026-11-07）：原报告11月3日发出；精确提交前后CPU剖析与微码对照于11月4日回复Dave Hansen，
发送后的内容及回复关系已核对。两封邮件的精确公开归档地址尚未核验。
本轮有界探索已收束，没有提出关闭保护的修复；处理器预测状态为何持续变化仍未解释清楚。

## 已确认结果

二分及父／子版分别对固定基线的计时定位到
[`a3af84b0fa00`](https://kernel.googlesource.com/pub/scm/linux/kernel/git/torvalds/linux/+/a3af84b0fa00ead01fcd0e28b5d773ff25990a0d)
（x86/bugs: Enable IBPB flush on BPF JIT allocation）。
父版为`96cce16e26dd02a8678f1e87f88a4b5cdb63b995`。下面的发行版对照与提交归因分开。

i7-12700KF、微码0x3e、未修改的Redis 6.2.6，单客户端、pipeline 256。
三个独立启动点，每端9次干净调用，每次含完整20命令序列的5轮原生重复。

| 指标 | 7.1.3首点 | 7.3 | 7.1.3回切 | 相对两基线均值 |
| --- | ---: | ---: | ---: | ---: |
| ZPOPMIN，请求／秒 | 999,365.83 | 871,396.84 | 1,000,946.61 | −12.87% |
| GET，请求／秒 | 3,548,521.06 | 3,551,131.59 | 3,547,932.59 | +0.08% |
| 完整测试生命周期，秒 | 61.396 | 61.704 | 61.301 | +0.58% |

ZPOPMIN每秒少约128,759次请求，组内CV为0.67%～0.75%，基线回切漂移+0.16%。
完整周期含服务启动、全部命令与重复、同步及清理，不能概括为“Redis整体慢13%”。

## 刷新后的持续影响

同一提交已有[stress-ng.seccomp报告](https://lists.openwall.net/linux-kernel/2026/08/19/369)，
其测试反复加载过滤器；我们的Redis测量窗口内未观察到BPF JIT分配及相应IBPB执行。

在未修改的快父版上，短命辅助进程依次在CPU0～19为自身开启间接分支保护，并全部退出；
之后才启动Redis，Redis没有继承该设置。两次独立启动重现11.06%／11.69%的ZPOPMIN下降，
空操作控制回切漂移−1.33%，完整测试时间只增加0.35%／0.17%。
独立诊断重现慢内核的返回预测失误模式：服务端精确定位到RET的失误采样由0／1升至624／626。
影响发生在保护动作结束之后，不是每次请求都重新执行刷新。

实测7.3已包含减少刷新触发的pack选择优化`a9b1f19a6a67`。
保留IBPB的RSB填充诊断也没有恢复吞吐；这些结果不构成撤掉安全保护的理由。

## 按上游要求补充的微码与CPU剖析

Pawan Gupta建议在同一内核上比较另一微码。每种微码均做空操作控制→触发保护→控制，
每次启动9轮无探针调用：

| 微码 | ZPOPMIN吞吐变化 | 完整测试时间变化 |
| --- | ---: | ---: |
| 0x3e | −12.03% | +0.27% |
| 0x37 | −12.14% | +0.24% |

54次调用、270份原生CSV独立复算通过；控制回切绝对漂移低于0.19%，最大组内CV1.40%。
临时`dis_ucode_ldr`启动核对了全部20个CPU，出现预期的旧微码标记；
其他报告的保护设置匹配，测试后恢复正常0x3e，没有刷写BIOS。

Dave要求看快慢两端的CPU开销分布。精确父版→子版→父版采样复用已有镜像、正常0x3e，
没有额外触发保护；每次启动先跑一次无探针调用，再以1999Hz做两次CPU-clock采样。

下表单位为CPU采样个数：每列取该启动两份profile的均值，每份合计该命令的五个原生窗口。
它与前面的无探针吞吐测量分开。

| 命令／执行位置 | 父版A | 子版 | 父版B |
| --- | ---: | ---: | ---: |
| ZPOPMIN，服务端内核 | 581.0 | 673.0 | 559.5 |
| ZPOPMIN，客户端内核 | 381.5 | 428.0 | 376.5 |
| ZPOPMIN，服务端用户态 | 408.5 | 442.0 | 407.0 |
| ZPOPMIN，客户端用户态 | 103.5 | 136.0 | 97.5 |
| ZPOPMIN，合计 | 1474.5 | 1679.0 | 1440.5 |
| GET，合计 | 286.5 | 291.0 | 293.0 |

新增ZPOPMIN采样约69%在内核，主要是服务端，分布在系统调用和网络路径。
增加的位置包括`do_syscall_64()`、`tcp_sendmsg_locked()`、
`__tcp_transmit_skb()`和`skb_release_data()`，没有单个主要新增热点。
[729行符号对照](bare-metal/commit-cpu-profiles.csv)保留两端控制、负差值和未知符号。

Dave在11月4日回复中未给出明确优化，建议继续调查。最后一轮有界CPU落点探索提示服务端核心更敏感，
但因原生客户端报错，在最终回切前停止；不将有效前缀当成已确认的核心归属或硬件内部机制结论。
后续Redis实验暂缓。

## 复现

保留完整原生命令序列：

```text
redis-benchmark --csv -c 1 -r 50000 -n 100000 -P 256
```

ZADD先填充集合，ZPOPMIN随后逐渐取空而不补充，所以请求包含空结果，不全是成功删除成员。
不能换成空库上只跑`-t zpopmin`。

见[独立复现步骤与实测辅助程序](reproducer/README.md)及[English](README.md)。
完整原始profile、失败与邮件保留在本地；这里的CSV是已整理、无私人路径的符号汇总。
