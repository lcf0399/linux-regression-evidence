# 有限 zswap 配额下的逐页统计刷新成本

这是对已有 zswap 限额统计刷新问题的补充证据：在匹配的裸机父版—子版—父版对照中，
`0efc297a3c49` 增加了单 worker、32 MiB 换出的 CPU 成本。随后在独立 MM 基线上，
验证了 Joanne Koong 已有层级 per-CPU 计数方案的派生版：保留原统计更新，有限额路径
的净收益明确；单 worker 无限额控制未检出明确代价，并发取舍仍不确定。

原三批分别回答“成本从哪里来”“已有方向能改善多少”“常用途径是否付出代价”，
不跨批次拼接百分比，也不将局部验证称为通用修复或应用加速。

## 场景与价值

程序在一个私有 cgroup 中准备 32 MiB 可压缩匿名内存，禁止 THP，设置
`memory.zswap.max=64 MiB`，再用 `MADV_PAGEOUT` 换出全部 8192 个 4 KiB 页。
限额没有被用满，也没有人为制造 OOM 或回收失败。随后重新访问并完整校验数据，释放内存。
8 worker 变体的总量仍为 32 MiB；无限额变体用作路径负对照，不是取消配额的优化建议。

有限配额可用于限制不同 cgroup 对共享 zswap 池的占用。这一用法有实际意义，但本程序
仍是合成测试，没有测量生产应用中出现的频率或业务损失。值得讨论的是：限额检查发生在
逐页存储路径上，单次刷新开销会累积，而且本次增量也体现在完整测试程序的 CPU 时间中。

## 1. 精确提交对照：确认成本来源

- 父版：`b0543d50c4cbc34ca612ab17c3cc9f2d174be8e0`。
- 子版：[`0efc297a3c4974dbd609ee36fc6345720b6ca735`](https://git.kernel.org/torvalds/c/0efc297a3c4974dbd609ee36fc6345720b6ca735)，`cgroup/rstat: avoid disabling irqs for O(num_cpu)`。
- 完整源码树只差该提交的 `kernel/cgroup/rstat.c` 修改；配置仅版本后缀不同，工具链相同。
- Intel Core i7-12700KF、20 个在线逻辑 CPU；LZO／zsmalloc，实际 full 抢占。
  完整配置及运行设置见 [bare-metal](bare-metal/README.md)；配置副本仅规范化本地签名密钥路径，不附密钥。
- 三个启动点，每条件固定 2 次预热、9 次正式样本；总计 18 次准入检查、81 份正式样本、18 份预热。
  路径检查与无探针计时分开。

| 指标，ms／32 MiB | 父版 A | 子版 | 父版 B | 相对合并父版 |
| --- | ---: | ---: | ---: | ---: |
| 单 worker、有限额，PAGEOUT CPU | 17.180 | 24.464 | 17.316 | +7.216 ms／41.84% |
| 同条件，完整程序及已等待子进程 CPU | 46.215 | 53.419 | 46.235 | +7.193 ms／15.56% |
| 8 worker、有限额，累计 PAGEOUT CPU | 283.082 | 298.696 | 288.385 | +4.54%，波动大，不定稳定幅度 |
| 8 worker、无限额，累计 PAGEOUT CPU | 43.438 | 43.890 | 43.520 | +0.95%，波动大，未见清楚差异 |

单 worker 主指标回切漂移为 0.80%，三个启动点的样本 CV 为 2.82%／2.13%／2.07%。
父样本范围 16.663～17.771 ms，子样本 23.506～24.922 ms，未重叠。
多 worker 两组的 CV 约 24%～43%，不能只引用它们的均值百分比。

### 机制与测量边界

有限额组在 PAGEOUT 区间执行 8192 次成功 zswap 存储和 8192 次限额内强制统计刷新；
无限额组同样成功存储 8192 页，但没有这些限额内刷新。该提交让统计刷新在处理每个
possible CPU 后释放并重取锁，以控制关中断时间。之前独立发行版诊断观察到每次刷新
1 组变为 21 组锁操作；这不是本轮逐锁计时，也未混入本轮干净样本。

原提交解决长时间关中断问题，其收益不能因本场景变慢而忽略。这里的历史父版仅用于归因，
不是推荐部署或撤回保护的方案。证据支持此提交在本条件下的成本贡献，不证明全部版本差异
都由它导致，也不证明可以安全延后统计、去掉限额或去掉让步。

主指标只计 worker 执行 PAGEOUT 的线程 CPU 时间。完整程序指标另含准备、恢复校验和
程序内清理及已等待子进程，不含外部 cgroup 创建／拆除或整机所有后台 CPU。
恢复可能命中 swap 缓存，不是冷解压或磁盘读取测试。压缩页最终释放、内容验证通过；
延后 swap 槽位记账单独保留，不将接口返回等同全部资源即时返还。

## 2. 已有计数方案：匹配 MM 基线验证

基线为 `2967f3ccdb5fae956f1b085370ec292bab5c7e25`；另一端只加
[实测派生补丁](prototype/hierarchical-with-rstat.patch)。配置仅版本后缀不同，工具链和运行设置相同。
这是对[作者公开实验实现](https://github.com/joannekoong/linux/commit/9092e0057f038ffca43ae3f35faf58c33b1d7c9b)
的适配，不是我们首次提出的算法，也不是原实验补丁的逐字复测。

原来每存一页，为检查限额就刷新整套统计；派生版改为单独维护压缩字节计数，检查时汇总
各 CPU 的计数。存入／释放时需同步更新祖先计数，原公开统计和回收仍依赖的 rstat 更新也继续执行。
这些额外更新成本包含在测量中；没有撤回 IRQ 延迟保护，也不是定时跳过刷新。

两端独立路径检查均成功存入 8192 页，有限额内强制刷新从 8192 次降为 0。
卸掉探针后，另做基线 A→派生版→基线 B，18 次启动准入、81 份正式样本及 18 份预热。

| 指标，ms／32 MiB | 基线 A | 派生版 | 基线 B | 相对合并基线 |
| --- | ---: | ---: | ---: | ---: |
| 单 worker、有限额，PAGEOUT CPU | 23.903 | 13.113 | 23.514 | −10.595 ms／44.69% |
| 同条件，完整程序 CPU | 49.247 | 38.569 | 49.363 | −10.737 ms／21.78% |
| 同条件，恢复及校验 CPU | 11.742 | 11.802 | 11.896 | −0.15%，未见明确变化 |
| 8 worker、有限额，累计 PAGEOUT CPU | 255.966 | 43.199 | 205.510 | 方向明确，幅度不稳定 |
| 8 worker、无限额，累计 PAGEOUT CPU | 37.150 | 42.024 | 29.211 | +26.65%，噪声及漂移大，未定性 |

单 worker 有限额主指标回切漂移 −1.63%，各点 CV 为 1.88%／3.55%／2.91%；
派生版样本 12.445～13.769 ms，基线 22.745～24.658 ms，未重叠。
完整程序 CPU 同时减少，不只是把成本挪到另一个已测阶段。

8 worker 有限额所有派生版 PAGEOUT 样本都低于基线，但基线回切漂移约 −19.71%，
派生版 CV 约 58.92%，不将描述性均值 −81.28% 当成稳定收益。
该组恢复及校验 CPU 均值增加约 61.60%，波动同样很大；完整程序 CPU 均值减少约 59.52%。
8 worker 无限额的完整程序 CPU 均值增加约 22.96%，也受噪声限制。
这些不利或不稳定结果全部保留，不能只引用有限额收益。详见[本批数据](bare-metal/counter-mm-pair/README.md)。

## 3. 单 worker 无限额控制：未检出明确额外成本

为单独观察不做限额刷新的常用途径，用相同内核配对新增 `unlimited1`，不重跑原噪声组。
程序只扩充条件选择，计时、数据和清理逻辑不变；这一独立批次共 6 次准入、27 份正式样本和 6 份预热。

| 指标，ms／32 MiB | 基线 A | 派生版 | 基线 B | 相对合并基线 |
| --- | ---: | ---: | ---: | ---: |
| PAGEOUT CPU | 12.225 | 12.208 | 12.093 | +0.049 ms／0.41% |
| 完整程序 CPU | 37.503 | 37.802 | 37.456 | +0.323 ms／0.86% |
| 恢复及校验 CPU | 11.594 | 11.534 | 11.589 | −0.057 ms／0.50% |

PAGEOUT 回切漂移 −1.08%，各点 CV 为 4.72%／4.74%／4.47%；完整程序 CPU 的 CV 为
1.97%／3.48%／1.79%。小幅均值变化没有形成明确额外代价，但这不是等价性证明，
也不能替代八 worker、深层 cgroup 或生产规模的结果。[独立控制数据](bare-metal/counter-unlimited1/README.md)。

## 正确性检查与未覆盖范围

两端共完成 16 项有效边界检查：叶／祖先零限额与近限额、动态修改限额、跨 CPU 释放后重用、
双 CPU 有界交接，以及子组实际退出后存活对象转归父组再扣账。内容及最终压缩对象清理通过。

首次动态限额检查有一次失败，原因是测试错误假设“预检查拒绝后不会回收旧条目”。
基线实际可以先回收再存入；修正后的检查直接核对两阶段返回，派生版保持相同行为。
该失败单独保留，没有计作通过。检查方案及限制见[补丁与边界说明](prototype/README.md)。

没有穷尽 RCU 竞态、CPU 热插拔、32 位、深层／大规模树；本轮再访问可能命中缓存，
也未独立验证冷解压性能。专用计数不是跨 CPU 的原子快照，不承诺原预检查本来没有提供的严格瞬时上限。

## 研究价值与适合讨论的问题

[原公开讨论](https://lore-kernel.gnuweeb.org/cgroups/CAO9r8zNxnVYpwrsuB1Ofcwf-Lks2e%2BDL1Ys9CXZ5jozBug_ybQ@mail.gmail.com/T/)
已经讨论限制刷新频率及专用计数方案。过期统计可能错误拒绝存储；替代计数也需要评估更新路径代价。
本材料补充裸机精确提交归因及保留原统计功能的派生版验证；所有表格数字来自本次研究，
没有把作者的测量当成我们的结果。

这条线值得作为已知问题的补充反馈：用途合理、逐页路径明确、有单提交证据，且有限额下
每 32 MiB 的绝对成本与完整程序 CPU 变化均可见。缺口是生产出现频率、业务影响及更大规模的更新代价。
因此当前结果支持讨论专用计数的取舍，不支持认定方案已全面安全、最优或没有常用途径代价。
优先讨论保留旧统计后的重复更新是否值得，以及维护者关注的层级、并发或缺页恢复条件；
不必为形成研究结果继续扩大合成压力矩阵。
