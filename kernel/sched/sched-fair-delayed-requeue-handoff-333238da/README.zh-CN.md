# MMTests管道交接吞吐与延迟重新入队记账

**发现来源：复现MMTests中的既有 `will-it-scale/context_switch1` benchmark。**
不是我们的源码／调用图或模型生成场景发现，不计入该方法的发现成果。

2026-10-30转为正式证据材料，准备向上游反馈；转正式不表示已经发送、上游接受或修复。
Mike Galbraith此前在另一种唤醒测试中定位过同一提交，本报告提供管道吞吐和归因的补充证据。

## 核心结果

每个worker与自己的辅助执行者通过两条管道交换单字节消息，往返计两次交接。
保留原生CORE绑核，在i7-12700KF的八个P核上运行，每核两个SMT逻辑CPU均可用；
超过八个worker时复用核心。线程／进程模式均已测量。

对照为 **v7.1.3 → v7.3 → v7.1.3**，下表相对两次基线均值，负数表示吞吐下降。

| worker数 | 线程模式 | 进程模式 |
| --- | ---: | ---: |
| 1／2／4／6／8 | −0.70%～−4.52% | −1.32%～−4.59% |
| 11 | −10.54% | −9.96% |
| 15 | −15.69% | −14.82% |
| 20 | −14.81% | −14.43% |
| 26 | −12.69% | −13.55% |
| 33 | −8.75% | −7.33% |
| 39 | −7.39% | −6.46% |
| 40 | −7.19% | −6.51% |

15-worker线程模式为 **10,875,243 → 9,168,152 → 10,872,945次交接／秒**，
v7.3每秒约少完成170.6万次。全矩阵最大组内CV为2.01%，最大基线漂移为1.39%。

独立的v7.2匹配对照仅撤回[`333238da9a19`](attribution/333238da9a19.patch)：

| 线程worker数 | v7.2原版A | v7.2诊断撤回版 | v7.2原版B |
| --- | ---: | ---: | ---: |
| 2 | 1,178,295 | 1,174,770 | 1,182,545 |
| 15 | 9,413,892 | 10,695,877 | 9,409,225 |

单位为次交接／秒。15-worker撤回后提高 **13.65%**，每秒多约128.4万次；
回切漂移−0.05%，最大CV为0.11%。2-worker控制变化−0.48%。

## 原因证据

该提交先更新当前实体，再计算延迟实体的lag补偿。这项记账有必要，撤回只用于诊断，不是修复建议。

独立诊断均使用与吞吐相同的后十五秒窗口：

- 15-worker每交接内核指令：v7.1.3的8,338条 → v7.3的10,423条（+25.00%）；
  v7.2匹配撤回则从10,239条降至8,355条（−18.40%）。上下文切换仍约每交接一次。
- 路径插桩中，v7.2每100次交接重新入队约1.0次（2-worker）与92.6次（15-worker），
  几乎每次都调用新增的`update_curr()`。撤回后内部调用消失，15-worker重新入队也降至55.3次。
- 实际CPU位置采样未发现比较两端整体放置模式切换。

证据指向延迟重新入队路径的额外工作。探针频率不是无探针运行的精确频率或函数独占耗时；
eligibility、实际放置与重新入队频率之间的完整关系尚未重建。
