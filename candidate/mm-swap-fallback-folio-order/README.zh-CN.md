# 匿名大页换出回退：调整拆分后小页的处理顺序

当前结论：**已有可讨论的局部优化，尚未发送。**在固定 MM 维护树上，单／双 worker
每处理 8 MiB，PAGEOUT 加缓存再访问的累计 CPU 时间减少约 **565／521 µs**
（**14.84%／13.14%**）。这不是应用整体加速幅度，也没有确定唯一引入提交。

## 用普通话解释

程序原先有几块 2 MiB 的连续大页。要把它们换出到本机文件型 swap 时，这条路径
不能整块处理，内核把它们拆成 4 KiB 小页。

问题不在于“多拆了一次”，而在于接下来小页的顺序：拆分代码按物理地址从小到大
放进队列，回收代码却从队尾取。因此原 head 之后的小页基本倒着交给后端。
在本机 NVMe／IOMMU 路径上，这使相邻内存的 DMA 映射不容易合并，CPU 要做更多映射工作。

[原型](prototype/reclaim-order.patch)只在这个换出回退点反转新子页的入队顺序，
让后续从队尾取出时按物理正序处理；不反转整个旧队列，也不改变公共拆页函数或迁移路径。
额外整理队列本身也有成本，当前实测已经包含它。

这是从 `swapfile.c` 探索出来的 F02，但**最终补丁改的是 `mm/vmscan.c`**。
它与 F01 的共享引用计数表清理不是同一项优化。

## 新 MM 基线的独立结果

基线为 `mm-stable 2967f3ccdb5f`（7.3-rc5），不是把旧 6.18 或 7.2 数据换名。
同配置、GCC 15.2；原版前 → 原型 → 原版后。每次启动、每个条件 2 份预热＋9 份正式，
合计 108 份正式、24 份预热，无样本筛选或补跑。

下表单位是 **µs／8 MiB 的累计 worker CPU 时间**，不是双 worker 的墙钟延迟。

| 条件 | 原版前 | 原型 | 原版后 | 相对两次原版合并 | 原版回切漂移 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基础页、单 worker | 3509.920 | 3524.923 | 3501.185 | +0.55% | −0.25% |
| 基础页、双 worker | 4239.868 | 4218.953 | 4228.021 | −0.35% | −0.28% |
| 初始大页、单 worker | 3804.692 | 3243.688 | 3812.945 | −14.84% | +0.22% |
| 初始大页、双 worker | 3978.957 | 3445.816 | 3955.020 | −13.14% | −0.60% |

两种大页条件的原型样本全部快于对应原版样本，最大组内 CV 为 0.97%／1.26%；
基础页变化较小、样本重叠，不能认定明显收益或退化。
计时之外另有 24 次非计时验证；两端 BIO 数都为 65，不是“磁盘请求减少了很多”。
同一调用线程观察范围内，IOVA 链接从 2,047 次降到 64 次，支持减少内部映射工作的解释。

## 为什么值得讨论，尚缺什么

价值在于已有“顺序变化 → 后端工作增加 → 局部原型减少工作并降低 CPU 成本”的证据链，
而不只有百分比。请求上游判断的是：**在换出回退点保留这种顺序是否合适，还是应由其他层处理？**

边界也要保留：

- 实测是主动调用 `MADV_PAGEOUT` 的合成测试，缓存再访问不是磁盘冷读。
- CPU 指标不含初始填充／合并、固定 20 ms 等待、完整数据检查和清理。
  含等待与校验的屏障区间仅改善 2.12%／1.27%，但它同样不是应用全生命周期。
- 只有本机、这份配置和 NVMe／IOMMU 后端的证据；没有真实应用整体收益。
- 成功路径已上机。失败／部分输出由源码和本地链表模型核对，不能称实际内核故障注入通过。
- 不声称已解释全部历史版本慢差；不添加没有证据的 `Fixes` 或维护者认可标签。
