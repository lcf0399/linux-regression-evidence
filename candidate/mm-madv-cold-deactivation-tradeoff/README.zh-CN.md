# MADV_COLD：MGLRU 去活跃化检查的状态相关取舍

[English](README.md) · [复现与计时边界](reproducer/README.md) · [数据复算](reproducer/verify_results.py)

`cc8ec7be78ff` 在页面已经属于最老一代时，跳过重复的 LRU 链表处理。
精确父版—子版—父版测试表明：这项优化确实有收益路径，但新填充页没有获得这项省略，
仍要支付新增检查的成本。下面同时报告两面，不建议直接撤回原优化。

## 用普通话解释

程序申请并填充内存，然后告诉内核：“这部分数据接下来不常用，但内容还要保留。”
这就是 `MADV_COLD`。它不同于 `MADV_DONTNEED`：后者可以直接丢弃原内容。

MGLRU 按代管理冷热页面；“最老代”是当前回收管理中的分类，不是固定等待了多少秒。
原改动会先判断：页面是否已经在最老代？如果是，就不必重复排队和移动链表节点。
如果不是，检查后仍会进入原来的处理，于是这次检查成为额外工作。
这里的“移页”只是调整回收链表，不是复制 4 KiB 数据。

测试没有直接改内核代号。新填充组通过正常映射、写入形成；文件页最老代组通过
一次私有 cgroup 主动回收请求准备。两端分别进行非计时观察，确认目标 4096 页
仍驻留且处于所需状态，再移除探针计时。仅仅调用过一次 COLD，并不能保证已进入最老代。

## 精确比较与结果

- 父提交：`9cbfd1c3c83b62c42ff46e17227e996cc9b2b336`。
- 子提交：[`cc8ec7be78ffaa29f6e0781fd12602974970eb53`](https://git.kernel.org/torvalds/c/cc8ec7be78ffaa29f6e0781fd12602974970eb53)，`mm/mglru: optimize deactivation`。
- Core i7-12700KF，单 NUMA、20 逻辑 CPU；worker 固定 CPU2，4 KiB 基础页、MGLRU=0x7、
  实际 full 抢占。两端工具链、相关设置一致，配置只差版本后缀。
- 每点每条件 9 个正式样本，父版回切；探针只用于另行准入。
  匿名页批次为 54 份正式程序；文件页批次为 27 份正式程序、54 个阶段样本。

## 机制证据与不能推出的结论

文件页匹配准入观察到：新填充组两端仍各有 4096 次入队／移页回调；最老代组父版
为 4096 次、子版为 0。它支持“新增检查在一种状态下是成本、在另一种状态下省去后续工作”。
尚未把检查内部每条指令的耗时分别计量。正式样本不挂探针；不能宣称逐份正式样本
都直接读过内核代号。

匿名页完整程序 CPU 只增加约 0.57%／0.47%，不是整个任务退化 12%。
文件页完整 worker CPU 的描述性变化为 −4.53%，但父版回切漂移 −8.05%，
因此不能认定整体稳定加速。整体范围包括各自的准备、校验和内部清理；
不包括外部 cgroup 创建／拆除及整机后台 CPU。局部指标也不是存储吞吐量或磁盘读取延迟。

[原作者的说明](https://lkml.iu.edu/2412.3/03612.html)针对高并发文件 I/O 的锁竞争；
还提到跳过链表调整可能改变最老代内部的回收先后。那是回收顺序副作用，
不是本测试发现的新填充页 CPU 成本。本测试没有复现其 400 并发 FIO 应用结果，
也不能断言作者已经明确接受了这里的代价。

## 实际价值与讨论范围

“保留内容，但暂时降低驻留保留优先级”是正常接口用途；成本按所处理页数重复支付，
本例单次绝对增量约 49～51 µs。因此它是具体、可复现的局部性能取舍，
而不是通过非法状态制造的问题。不过仍是合成测试：没有量出真实应用的调用频率、
累计损失或延迟预算影响，不能把局部百分比外推到应用。

值得讨论的是：在保留最老代跳过处理的收益和必要并发保护时，新填充页的检查成本
是否有更合适的实现。后续 [MGLRU-FG v4 的相关重构](https://lkml.iu.edu/2610.1/19350.html)
已包含引用计数为零时跳过原子写等变化，但它还改变计数与生命周期处理，
并非已在本场景验证的单行修复；本数据没有测试该系列。
2026-10-20 核对的[主线 `f47d223627f8`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/mm/folio.c?id=f47d223627f80cb7a1eb14c585fe6cb35de5e984)、
[mm-stable `2967f3ccdb5f`](https://git.kernel.org/pub/scm/linux/kernel/git/akpm/mm.git/tree/mm/folio.c?id=2967f3ccdb5fae956f1b085370ec292bab5c7e25)、
[mm-unstable `3eb3e848d72c`](https://git.kernel.org/pub/scm/linux/kernel/git/akpm/mm.git/tree/mm/folio.c?id=3eb3e848d72cde2156447cc960ca321bb2ac41a9)
的相关 helper 仍保留清引用／最老代检查。
这些源码核对不等于在新树上复现了同幅慢差。
