# 默认时间片参数未变的调度更新

第四版在v7.2上把重复设置默认参数的成本从 **616.51降到162.39 ns/次**，节省 **454.12 ns（73.66%）**。
已有的自定义时间片快捷路径增加约0.65 ns（0.40%）。这是系统调用微基准结果，不是应用整体加速。

第四版还在已测组合中处理了Peter指出的两项等值边界：默认／自定义模式切换，以及RT-PI解除后的隐含uclamp重置。
原版和第三版都复现了这两项遗漏，不能写成它们也通过了这两项检查。

[English](README.md)

## 场景与原因

普通SCHED_OTHER、nice 0线程反复对自己调用`sched_setparam(0, {.sched_priority = 0})`，没有请求改变参数。
主项使用默认时间片，对照使用10 ms自定义时间片。PI只属于正确性检查，不是性能主测试。

默认模式下，旧接口封装用`attr.sched_runtime = 0`表示默认请求，而`p->se.slice`保存实际时长。
直接比较两者会把本来没变的参数视为需要更新。第四版先比较模式、再比较时长；
默认值已变化、隐含clamp需要重置或任务当前不在fair类时，仍走更新路径。显式uclamp路径保留。

## 平台与边界

- Intel Core i7-12700KF裸机，计时线程固定CPU 2，普通SCHED_OTHER／nice 0。
- 原型对照均基于v7.2、GCC 15.2，Kconfig符号仅LOCALVERSION不同。
- 各计时点每场景3轮预热、15轮正式样本，每轮500,000次调用；实际full抢占，performance governor/EPP，关闭turbo。
- 探针与计时分开；计时包括调用循环和返回值检查，不是裸内核函数耗时。回切漂移和CV分别列出。
- 九月版本对照与十月补丁对照的构建及启动设置不是同一完整身份，不能跨轮相减，也没有完整解释原6.5%～7.1%慢差。
- 未证明真实应用收益或穷尽所有配置、并发状态；已测语义、局部性能与上游是否接受分别看待。
